# 高温防护阶梯 —— 设计计划

把「温度到 95°C 就把风扇拉满」的**单阈值保护**，换成分级、且每一级有**最短保持时间**的阶梯。

起因：默认模式下安全模式反复触发 —— 风扇转几秒就停、间歇性出现（用户回报）。

- 状态：**已实现**（1.0.0）
- 相关：[upstream-divergence.md](upstream-divergence.md)（本功能是对上游的**刻意分歧**）· [todo.md](todo.md)（§5 的遗留项）

---

## 1. 上报的现象与诊断

**现象**：默认模式下突然进入安全模式 → 风扇转几秒 → 很快又停 → 间歇性出现。

**结论**：不是芯片真的过热，也不是假传感器 —— 是三个问题叠加。

### 1.1 阈值正好落在热点传感器的自然波动区间内

负载下每 2 秒采样一次（Mac16,1 / M4）：

```
03:08:36   88.7
03:08:38   96.8   ← ≥95 触发 → 风扇拉满
03:08:42   95.0
03:08:45   97.6
03:08:51   95.0
03:08:53   88.5   ← <90 解除 → 交回系统（风扇常直接停）
03:09:03   93.3   ← 又爬回阈值以上 …
```

日志里同期的 2 秒变化量：`−6.0 / −11.3 / −10.1 °C`。
**风扇不可能在 2 秒内降温 11°C —— 是读数本身在跳。**

触发线 95 与释放线 90 之间只有 5°C，**比传感器自身的摆动还窄** → 必然 bang-bang。

### 1.2 没有去抖，也没有最短保持

- 判定跑在 **10Hz**：2 秒内有 20 次机会，**任意一次**采样 ≥95 就把风扇拉满
- 释放同样只看单次采样：一次 <90 就放行
- 于是「转几秒就停」

### 1.3 默认模式下本就不该介入

默认模式（`FanProfile.silent`，`curve.handsOff == true`）的语义是**「风扇交给系统」**。
此时 SMC 有自己的（滤波后的）热管理，我们再插一脚就是**两个控制器抢一个风扇**。

## 2. 阶梯设计

### 2.1 用户定稿的规则

| 条件 | 动作 |
|---|---|
| ≥ **90°C** 持续 **10 秒** | 转速 = 最大转速的 **50%** |
| 半速下 ≥ **95°C** 持续 **30 秒** | 转速 = **最大** |
| 满速运行 **30 秒**后，若 < 95°C | 回到 **50%**（不直接停） |
| 半速运行 **30 秒**后，若 **< 85°C** | **停止**，交回所选模式 / 系统 |

### 2.2 实现方式

纯状态机 `HighTempProtection`（`Sources/SmartFanCore/HighTempProtection.swift`），
只做判定、不碰 SMC，和 `ThermalFloor` 同风格 —— 任何一个转折都能离线单测。

> **为什么需要掉档宽限**：最初写成「一次采样掉到阈值以下即归零」，
> 于是 **100ms 的一次抖动就作废了将近走完的 30 秒窗口**。
> 用实测轨迹回放（`回放脚本已删，结论记录于此`）：
> 同一温度带改成 100ms 级抖动后，满速档位立即可达（`half=28s full=12462s`）；
> 而**温度真的在 97–100°C**时，满速在 30 秒时准时到达（`half=20s full=370s`）。
> 反过来说，若读数**大部分时间在 95 以下**（实测轨迹是 48 秒里只有 12 秒 ≥95），
> 阶梯就停在一半 —— 这符合"读数基本没到升级线"的含义，不是缺陷。

- 每一级**至少保持 30 秒**才可能下调 → 抖动被时间维度吃掉，这是消除 bang-bang 的关键
- **释放回差 5°C**（`releaseGap`）：触发线 90°C，释放线 85°C。没有回差时，释放线正好落在
  "机器在干活"时读数的中位数上 —— 现场实测见 §7
- **掉档宽限 3 秒**：计数不因单次采样掉线而归零，只有**连续低于阈值超过 3 秒**才重新计时；
  且计数**只累计真正在阈值以上的时间**（掉档期间冻结，不虚增）
- **下阶梯与上阶梯同样分级**：满速 → 半速 → 停止，不会从满速直接掉到 0
- 阶梯是**温度响应，不是模式响应**：切换模式不会取消它（芯片还热着）；唯一例外是切到「交给系统」的模式

## 3. 两个开关

位置：**首选项 → 风扇页**。

| 设置 | 默认 | 关掉之后 |
|---|---|---|
| **高温防护** | **开** | **永不启用**；若阶梯正在持有档位，下一 tick 立即释放 |
| **在「默认」模式也生效** | 关 | 默认模式（交给系统）下完全不介入 |

两者都持久化在 `UserDefaults`（`highTempProtection` / `protectionInDefaultMode`）。

## 4. 与守护进程热保护的分工

守护进程有另一个独立的 `ThermalFloor`（`DaemonInvariants.swift`），
它的触发条件是「**自己正持有一个非最大转速的 hold**」。

- 默认模式**没有 hold** → 它本来就不会触发（所以上报的现象 100% 来自 App 层）
- 但阶梯在半速时会持有一个 **50% 的 hold** → 守护进程若仍用 95°C，就会把风扇直接拉满，
  **把阶梯的中间档位架空** → 形成第二层 bang-bang

因此把守护进程的阈值抬到 **105°C / 清 100°C**（`FanProfile.emergencyTempThreshold`），**高于阶梯的作用范围**：

| 谁 | 负责 |
|---|---|
| App 阶梯 | **90–100°C 的分级响应**（守护进程读取同组传感器，故其阈值取到 105） |
| 守护进程 `ThermalFloor` | 「客户端已经不再响应、却还持有低转速」的**应急兜底** |

> **为什么是 105 而不是 100**：两层读的是**同一组热点键**，而阶梯从 95 升到满速要 30 秒。
> 若守护进程取 100，它会在这个升级窗口内抢先拉满，把中间档位架空 —— 仍是抢风扇。
> 105 比阶梯上限高 10°C，留出足够余量。

> ⚠️ 两点要注意：
> 1. 这是**刻意分歧**（上游两处都是 95）→ 已记入 [upstream-divergence.md](upstream-divergence.md)
> 2. 守护进程的兜底**不受「高温防护」开关控制** —— 它是最后一道防线，不是用户的安全模式。
>    如需「不勾选就彻底没有任何保护」，需要改守护进程协议（把开关传给它），目前未做。

## 5. 传感器基：阶梯已修，曲线仍是原样

> **2026-10-04 更新**：阶梯（本功能）**已改用校准过的真实核心读数**，见 §7。
> 下面这一节现在只适用于**上游的模式曲线**（它们仍照 `safetyPeakTemp` 标定，未改动）。

### 原记录：安全层的传感器基 ⚠️

**已确认，但本次不修**（用户决定先记下来）。

`safetyPeakTemp`（`FanControl.swift`）取的是 `thermalKeys` 中 **`TC*` / `Tp*` / `TG*` / `Tg*` 全部键的最大值**，
其中包含我们自己在 `ThermalStatus+Display.swift` 里标注为「**不是核心温度**」的键：

- `TC*` 家族在不同芯片上行为不同：M4 Max 上 `TCDX`/`TCMb` 是 **SoC 级热点**（GPU 负载下 88/92°C，而 CPU 核心只有 47°C）；
  但在 **Mac16,1 这台 M4 上只有 `TCHP`/`TCMb`，且 `TCMb` 十次采样都与最热核心完全相等**（它是核心最大值，不是热点）
- `Tp*` 每四个一组，**只有一个是真的核心温度**，其余是另一个量：负载下比核心高；组内键在某些核心关闭时读 0.0

负载下实测 12 次采样（**应用实际读取的键集合**，即 `safetyPeakTemp` 与 `displayedCPUTemp` 对比）：

| | 安全层（`safetyPeakTemp`） | 真实核心（`displayedCPUTemp`） | 差值 |
|---|---|---|---|
| 最大值来自 | **`Tp0W`**（12/12 次） | 校准核心键 | |
| 范围 | 89.9 – 96.9°C | 82.7 – 93.8°C | **+3.1 ~ +9.6，平均 +6.8** |

也就是说，「95°C 保护」实际是「**真实核心约 88°C 就介入**」。

> ⚠️ **订正**：本文早期版本把这组数据写成「键 = `TCMz`，+6.3~+11.7」。那是错的：
> 当时用的是 `smart-fan discover`（**全量 SMC 键**，包含 `TCMz`），而应用只读 `thermalKeys` 那~66 个键，
> **`TCMz` 不在其中**。结论（偏差约 7–9°C）不变，但**键名与区间以本表为准**。

测试里白纸黑字记着这件事（`DisplayedTemperatureTests`）：

```swift
#expect(s.cpuTemp(coreKeys: ThermalStatus.m4CoreKeys) == 62.3)
// Fan control and the safety floor still see the hotspot, as upstream.
#expect(s.safetyPeakTemp == 75.2)
```

**建议的修法（待办）**：让 `safetyPeakTemp` 改用**与界面相同的基** —— `max(最热真实核心, 最热 GPU)`，
即面板显示的那个温度。这样「面板显示 X°C」与「安全层看到 X°C」一致，95°C 才真的是 95°C；
没有校准键表的芯片自动保持现有行为（兜底不减弱）。守护进程读同一个值，一处改动两层都修。

因为阶梯现在有了 10 / 30 秒的时间维度，这个偏差的危害**从「抖动」降级为「提前约 7°C 介入」**，不再紧急。

## 7. 现场问题：一直停在半速（2026-10-04）

用户回报"一直是防护中，半速运行，停不下来"。60 秒连续采样（每 0.5 秒）给出定论：

| | 控制基准（`safetyPeakTemp`） | 真实核心（`displayedCPUTemp`） |
|---|---|---|
| 范围 | 85.9 – 96.9 | 78.3 – 94.8 |
| 中位数 | **90.8** | 85.6 |
| ≥90 时间占比 | **55%** | 2% |
| 连续 ≥95 最长 | **2.0 秒**（升级需 30 秒） | 0 秒 |
| 连续 <90 最长 | **23.0 秒**（解除需 30 秒） | **59 秒** |

**两个症状同一个根因**：阶梯读的 `safetyPeakTemp` 含非核心键，中位数**恰好压在触发线 90 上**，
于是：

- **停不下来**：解除需要连续 30 秒 <90，而最长只有 23 秒 → 永远不满足
- **升不上去**：升级需要连续 30 秒 ≥95，而它每 2 秒就抖过 95 又掉回来 → 同样永远不满足

而真实核心中位数只有 85.6°C —— **机器并不热，是读数虚高**（§5 的偏差）。

### 两处修改

1. **阶梯改用校准读数**：`protection.evaluate` 现在拿 `status.displayedPeakTemp`
   （最热真实核心 + GPU），不再是 `safetyPeakTemp`。只动本功能 —— **上游曲线与持续窗口的基不变**，
   所以 55/65/85 那几条线不需要重标定
2. **补上释放回差 5°C**（`releaseGap`）：触发 90°C、释放 85°C。没有回差时释放线正好落在
   工作负载下读数的中位数上 —— 这本身就是"停不下来"的第二个原因

钉子测试：`MonitorRecoveryTests.protectionBasisIsTheCores` —— 派生键 95°C、真核心 80°C 时
**不得介入**；真核心 92°C 时仍要介入（证明是收窄了基，而不是抬高了阈值）。
